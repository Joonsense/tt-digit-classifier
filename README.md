# A digit classifier made of logic: 80 MACs per clock in two Tiny Tapeout tiles

[![Draw a digit. The chip answers in 8 clocks.](docs/card.png)](https://joonsense.github.io/tt-int4-dot-accelerator/)

**[Draw a digit in the browser and watch this chip's arithmetic answer](https://joonsense.github.io/tt-int4-dot-accelerator/)**

The whole model is the chip. A 64 to 10 handwritten digit classifier, with its 640 four bit weights compiled into
sky130 logic as constants. Send an 8 x 8 image as 8 bytes, one per clock; four clocks later the digit is on the 7 segment
display. Back to back that is **one image every 8 clocks: 80 multiply accumulates per clock, 6.25 million images per
second at 50 MHz**, with no weights to load and no host arithmetic.

Designed and verified by an AI agent pipeline. **It has not been fabricated**; layout numbers come from the official
Tiny Tapeout GitHub Actions flow on this repo.

## Numbers

| | |
|---|---|
| Throughput | 1 image per 8 clocks, 80 MAC/clock (measured back to back over all 360 test images) |
| Accuracy | 91.39% on the 360 image test split (float model: 95.83%) |
| Bit exactness | all 3,600 class scores read back from the chip equal the Python integer model |
| Area | 1x2 tiles, 75.0% placement utilization |
| Timing | 50 MHz, setup slack +5.26 ns at the slow corner (ss, 100C, 1.60V) |
| Signoff | DRC 0, LVS 0, antenna 0, Tiny Tapeout precheck passed, gate level tests passed |
| Power (estimate) | about 1.5 mW at 50 MHz, typical corner (LibreLane report) |
| FPGA | builds for the iCE40UP5K Tiny Tapeout simulator board: 1,076 of 5,280 logic cells, 28.7 MHz max ([bitstream](https://github.com/Joonsense/tt-digit-classifier/releases/tag/fpga-v1), not tried on a board) |
| Fault check | the tests fail on a build with one bias off by one (360 scores differ) |

Timing took four layouts. The first missed the slow corner by 0.65 ns: every pixel pin fanned out to about 80 gates,
which pre layout timing cannot see. Registering the inputs closed it at +0.14 ns. Registering each row's sums moved the
critical path to the 10 way comparison (−0.004 ns), and splitting that comparison in two closed it at +5.26 ns.
Latency is 4 clocks; the rate is still one image per 8 clocks.

## Why a fixed model, and why two tiles

A general accelerator on these 8 data pins tops out at 8 MAC per clock with 1 bit activations
([tt-lowbit-dot-accelerator](https://github.com/Joonsense/tt-lowbit-dot-accelerator)): the weights have to come in
through the pins, and so do the results going out. Freeze the weights into the logic and both costs disappear. Each
input byte now feeds all 10 classes at once, so the same pins carry 10 times the work.

The cost is area: ten parallel score adders plus the pipeline are about 14,700 um2 of cells, more than one tile holds. The sweep that
decided the structure is in `model/`: grouping 4 pixels into one constant table per class was the smallest form
(10,700 um2 for the core; a whole byte table was 13,100). Cutting weights to 3 bits would not have saved it either:
accuracy fell 2 to 4 points.

## Pins

| Pin | Direction | Function |
|---|---|---|
| `ui_in[7:0]` | in | one image row, pixel 0 (left) in bit 0, 1 = ink. With SCORES high: class number to read |
| `uio[0]` | in | IN_VALID |
| `uio[1]` | in | ABORT (restart the current image) |
| `uio[2]` | in | SCORES: `uo_out` shows the signed score of class `ui_in[3:0]` instead of the display |
| `uio[3]` | out | DONE, toggles on each new result |
| `uio[7:4]` | out | the digit, binary |
| `uo_out[6:0]` | out | 7 segment a to g (blank until the first result) |
| `uo_out[7]` | out | DONE (decimal point) |

## Files

- `src/core.v`: generated by `model/generate.py` from `model/digits-int4-a1.json` (`model/train.py --act-bits 1` makes that file)
- `test/test.py`: all 360 test images back to back, all 3,600 scores, ABORT and input gaps (RTL and gate level)
- `host/classify.py`: demo board MicroPython script with real test images. Not yet run on hardware.
